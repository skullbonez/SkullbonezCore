## Findings

### High - Plan 12's profiler fix can be satisfied by a no-op null check

- Plan evidence: `engine-cleanup-plans/12-ambient-singletons-log-profiler.md:103`
  says to "rebind it on backend recreation, or null-check before use in
  `ReadPendingGpuResults`".
- Current source: `SkullbonezSource/Core/Profiler.cpp:528` defines
  `ReadPendingGpuResults`, and `SkullbonezSource/Core/Profiler.cpp:530` already
  copies `m_renderDiagnostics` before checking it. Other profiler GPU paths
  already null-check the same borrowed pointer at
  `SkullbonezSource/Core/Profiler.cpp:461`, `:485`, `:499`, and `:514`.
- Current source: `SkullbonezSource/Core/Profiler.h:294` still describes
  `m_renderDiagnostics` as a startup-bound borrow.

Why this matters: a dangling pointer is not made safe by checking it for
non-null. A smaller model could add or point to an existing null check, mark
2.1 complete, and leave the backend-recreation hazard intact.

Fix the plan before execution: require one of these structural end states:
`Profiler` is rebound on every backend recreation, the backend owner clears the
borrow before teardown and rebinds after recreation, or the profiler stores a
non-dangling owner-mediated handle. Remove "or null-check" as an accepted fix.

## Sequencing Safety

The main execution order is mostly safe: mechanical DisjointSet first, then
small singleton work and `.inl` promotion, then render/runtime decoupling, then
the large Run/replay/solver plans. The hard gates are generally placed in the
right areas:

- Physics determinism: plan 02, plan 04 physics conversions, plan 10
  `SimulationController`, and plan 12 diagnostics-sink work correctly require
  `tools\validate_physics.bat`.
- DX12 zero-validation: plans 08, 10, and 11 correctly attach
  `tools\validate_dx12_renderer.bat`, and plan 11 correctly requires three runs
  for resource-state changes.

Unsafe or underspecified sequencing:

- Plan 03 should not be "any time" unless plan 05 has already supplied the
  replacement behavioral checks or a human explicitly accepts review-only
  enforcement.
- Plan 10/13 should not send a worker through FAC-001 because the aggregate is
  already absent from live source.
- Any step that says "replay scrub" or "interaction automation" should name the
  exact script before a smaller model executes it.

## Acceptance Criteria Review

The strongest acceptance criteria are structural: delete `IRenderBackend`, delete
or split `EngineContextBindings`, remove `SimulationController::System`, remove
static mutable `RenderHelper` state, make `RunSolverPhysics` a short stage
driver, and add tests that directly reference the new behavior. These cannot be
satisfied by a rename.

Weak or rename/no-op-prone criteria:

- Plan 12's "null-check before use" can be satisfied without fixing the dangling
  pointer hazard.
- Plan 04's "throw count materially reduced from 283" uses a stale baseline and
  could reward count-chasing instead of lane-correct conversion.
- Plan 03's "no `MAX_*` frozen-count budget" is measurable, but only proves the
  regex names are gone. It needs the invariant inventory to prevent accidental
  deletion of real checks.

## Completeness And Scope

The plan set covers the major architecture cleanup pressure points visible in
the current source: `Run`, `PhysicsWorld`, replay, render helper state,
RenderGraph/backbuffer state, EngineContext, error handling, allocation policy,
and test coverage.

Potential missing or under-owned work:

- FAC-005 has no numbered owner plan in this bundle. Plan 13 correctly flags it,
  but the campaign checklist never schedules it.
- Device recreation / resize proof is named in plan 10, but no exact validation
  or reproduction command is given.
- Plan 05 should produce the coverage map before plan 03 is allowed to remove
  checker-backed gates.

Potential over-scope for a solo hobby engine:

- Plan 03 and plan 07 are policy-heavy and intentionally require human decisions.
  Their STOP gates are appropriate.
- Plan 01's total Run decomposition is large. The plan is acceptable only if it
  stays action-group sized and tests are added as each command-table slice lands.
